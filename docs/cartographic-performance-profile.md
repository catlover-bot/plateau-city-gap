# Cartographic interaction performance profile

Goal: `cartographic-interaction-performance-v1`

Milestone: P0 — Performance Profile

Date: 2026-09-02 JST

This profile records the unoptimized C5 implementation at commit `25a19ee9ebf444fb2244de6ace625238a74bbb89`. It changes no product behavior. The raw five-sample record is [`analysis/outputs/real/cartographic-performance-profile-baseline.json`](../analysis/outputs/real/cartographic-performance-profile-baseline.json), generated by [`frontend/scripts/profile-cartographic-performance.mjs`](../frontend/scripts/profile-cartographic-performance.mjs).

## Measurement contract

- Production build and local Vite preview.
- Five fresh browser contexts at 1440 × 900, reduced motion, service worker blocked.
- The external GSI basemap is intentionally blocked. This makes local-vector readiness reproducible and exercises the documented C5 degraded state instead of treating a remote tile response as PLATEAU readiness.
- `cold` means the first activation of that path in a fresh page after the existing C5 all-artifact derivative has become ready.
- `warm` means the second activation of the same path in the same page.
- Story ready requires the requested story, ready local MapLibre sources, and a rendered thematic building feature.
- Exact-target ready requires the target step, exact source geometry in `public-target`, ready local MapLibre source, and a rendered exact feature.
- Facility ready requires its registered-position marker plus essential local Area sources. It never substitutes a point for an exact PLATEAU target.
- Two animation frames after semantic readiness are reported separately as compositor stabilization.

The C5 checkpoint remains the canonical before UX record: FMR median `1125 ms`, 800 m Area ready `288 ms`, building-use `4135 ms`, exact road `2453 ms`, exact building `12336 ms`, and facility reference `5057 ms`. The P0 cold/warm profile adds a stricter repeatable decomposition. P4 will compare the optimized implementation with this P0 record using the same timestamp meanings and browser conditions.

Every path resubmits Area, mask, all 4,898 buildings, all 1,686 roads, all 55 planning objects, target, and origin. Some cold building/facility transitions execute the whole effect twice. No path added or removed a MapLibre source or layer, and the map instance was recreated zero times. C5 already fixed map recreation; P1–P3 must preserve that success while eliminating redundant data and style work.

The production React bundle has no React Profiler markers, so a component-render count is not directly observable without changing the product being measured. The probe instead records the public render-key/readiness mutations and every side effect of the React map effect. Median mutation counts range from 24 for a story switch to 170 for a road target; this, the delayed first `setData`, and duplicate full-effect execution are the relevant production evidence.

Garbage-collection pause attribution is likewise not exposed without intrusive V8 tracing. Heap deltas, long tasks, script duration, task duration, nodes, layouts, and style recalculations remain in the raw record. Median heap deltas ranged from approximately −1.5 MiB to +9.5 MiB, consistent with allocation and later collection but not sufficient to name a particular pause as GC.

## Root cause by path

### A. Building-use story

- Derivative dependency: yes. C5 cannot render this story until the complete building, road, and planning bundle has loaded, even though only buildings are visible.
- Fetch/parse: the 4,898-building artifact dominates bytes and parse time. Roads and planning are unrelated to this story but arrive in the same `Promise.all`.
- Render: switching the story resubmits all 6,643 derivative features and changes 46 paint/layout/filter properties.
- Recreation/retry: no map, source, or layer recreation; no duplicate artifact fetch.
- P2 direction: lazy story-specific loading, source/version/hash cache keys, bounded post-summary prefetch, and reuse of an unchanged building source.

### B. Exact building target

- Derivative dependency: yes. Exact identity is resolved by scanning the full building collection, so a one-object target is coupled to the 3.24 MiB building artifact and the unrelated road/planning artifacts.
- GeoJSON/React-to-map delay: the median first `setData` does not occur until 1.63 s cold / 1.45 s warm after the action.
- Render: the cold median includes two full submissions—13,286 features—and 108 style/filter changes. The worst warm sample takes 40.95 s while preserving the same semantics.
- Camera: median `fitBounds` invocation follows the first map effect at about 1.64 s cold; camera invocation is not the primary cause.
- P1 direction: exact unmodified source geometry in a small identity-addressable target derivative, without waiting for Area context.

### C. Facility reference target

- Derivative dependency: semantically none; it is a registered position. The current presentation object nevertheless retains the full cartography bundle and the map effect resubmits it.
- GeoJSON/React-to-map delay: first `setData` is 2.37 s cold / 0.74 s warm.
- Render/readiness: the marker is local, but unrelated source processing and persistent failed basemap requests compete with it. Cold and warm medians are 4.45 s and 3.60 s.
- Basemap: the fixed degraded protocol generated 401–497 aborted tile requests per fresh page. Basemap completion is not part of semantic readiness, but the retry volume is observable scheduling noise.
- P1/P3 direction: render the local marker with only essential Area context; keep the honest degraded notice while bounding external-basemap retries.

### D. Exact road target

- Derivative dependency: yes. One exact road polygon is resolved from the full 1,686-feature road artifact after the all-artifact load.
- Render: all 6,643 features are resubmitted and 74 paint/layout/filter operations run for each activation.
- Camera: `fitBounds` is invoked at a 73 ms cold median, so camera initiation is not the bottleneck. Map/source processing continues afterward.
- P1 direction: a target-only derivative retaining the same road object ID and exact polygon coordinates.

## Basemap, retry, and readiness

All five successful samples have zero page errors, zero failed same-origin requests, and zero duplicate cartography fetches. The intentionally failed external basemap does not block local semantic readiness, but hundreds of tile aborts demonstrate that its lifecycle is not bounded after failure. P3 must stabilize this without changing basemap choice or weakening the local-vector ready gate.

The probe originally observed one 120-second facility-ready timeout during an uncontrolled external-basemap run. It is not mixed into the five-sample controlled dataset, but it is retained here as profiling evidence for the P3 retry/resume and readiness audit.

## Optimization decisions locked by evidence

1. **P1 target fast path:** generate provenance-complete, identity-addressable exact building and road artifacts from the same CityGML source/version; load them on bounded user intent. A facility marker must not depend on any PLATEAU story artifact.
2. **P2 story loading:** stop the unconditional all-artifact `Promise.all`; load only a selected story's Area-scoped derivative, cache by source/version/hash, cancel stale requests, and allow bounded idle prefetch only after result intent.
3. **P3 lifecycle/readiness:** make unchanged GeoJSON and style values no-ops, avoid duplicate effect application, retain the map/source/layer instances, bound basemap failure behavior, and preserve exact semantic ready definitions.
4. Initial FMR and Area selection must not gain a heavy derivative request. C5 visual design, copy, story definitions, Area/Unknown semantics, target grammar, and provenance remain unchanged.

P0 contains no claim that the performance targets are met and no human or municipal result.
